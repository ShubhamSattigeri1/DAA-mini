How it works

The app is split into an HTML/CSS/JavaScript frontend and a Java solver. When you select Solve, the frontend validates the cell values, sends the grid as JSON to the local Python server, and the server launches the Java source file as a subprocess. The grid size is passed as an argument and the puzzle is sent over standard input. Java returns the solved grid on standard output; validation and solving errors are returned on standard error and shown in this interface.

The Java source-file launcher requires JDK 11 or newer. Each solve starts a new Java process and has a 30-second timeout.

Backtracking algorithm

Backtracking builds a solution one empty cell at a time. At each step, the solver finds a legal value, tentatively places it, and continues recursively. If that choice eventually leaves an empty cell with no legal values, it undoes the placement and tries another candidate. If every candidate fails, it reports that the puzzle is unsolvable.

  1. Validate clues: Check that every given number is in range and that no number is repeated in a row, column, or sub-grid.
  2. Choose an empty cell: Scan the remaining empty cells and select the one with the fewest legal values. This is the minimum remaining values (MRV) heuristic; it tends to expose dead ends early.
  3. Try candidates: Test values from 1 to the grid size against the row, column, and sub-grid constraint tables.
  4. Recurse or undo: Mark a candidate as occupied and recurse. If it fails, clear the cell and its constraint marks, then try the next candidate.
  5. Finish: When no empty cell remains, all constraints are satisfied and the completed grid is returned.

The Java solver keeps the grid in a two-dimensional integer array and tracks used values with boolean lookup tables for rows, columns, and sub-grids. These tables make each candidate legality check constant time. The solver modifies the grid in place and undoes failed choices instead of copying the whole board.

Time and space complexity

Let N be the grid width (4 or 9) and E the number of empty cells. A loose worst-case search bound is O(NE+3): there can be up to N candidate choices for each empty cell (O(NE) search nodes), and this implementation scans up to N² cells and checks up to N values per cell to choose the MRV cell (O(N³) per node). This is an upper bound, not a prediction of typical runtime; clue constraints and MRV usually prune the search substantially.

The board and row/column/sub-grid lookup tables use O(N²) space. Recursive search uses up to O(E) stack frames; candidate lists held by those frames use up to O(E × N) additional space. Validation before the search takes O(N²) time.

Input and error handling

  • Use 0 for an empty cell and values from 1 through the selected grid size.
  • The frontend rejects fractional, missing, or out-of-range values before starting Java.
  • The backend checks the grid dimensions, numeric values, and duplicate clues.
  • A well-formed board with no valid completion is reported as unsolvable.
  • Missing Java, process timeouts, and malformed solver responses are surfaced as errors instead of displaying a false solution.
